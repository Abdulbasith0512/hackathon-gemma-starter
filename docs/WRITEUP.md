# Asset Intelligence Copilot: write-up (draft, 2 pages)

## Page 1: system design

**Goal.** Answer operators' plain-English questions about the wells correctly and with evidence, keep what people tell it, and never let a language model do the arithmetic.

**Data: storage, indexing, retrieval.** The documented dataset folders load into SQLite in about 2 seconds (cached after that): wells, ~39.6k inspections, ~5.7k repairs, regulator events and notes, indexed by well and time, by date, and by the inspection that triggered each follow-up record. Every record keeps its source file and line and its original JSON, so the evidence panel can show exactly what was used. The manuals, SOPs and 1,509 repair reports are split into citable sections with SQLite full-text search. Reports are found only through each repair's `report_file`; containment times and compliance tables are parsed from them. Thresholds and deadlines (production temperature per well type, spill classes, SR-01..SR-03, RC-01..RC-04, the root-cause trigger) are read from the manuals and SOPs at load time and keep the quoted passage; a missing number is shown as a fallback, never silent.

**Tools.** 24 deterministic Python tools: status, wells not producing, temperature series, spills, downtime, downtime ranking, repair costs and repairs, who carried out a repair (technician from the user records, "not recorded" when it is missing), gas-odor reports against the OPS-1 response deadline, spill heatmap, root-cause candidates, compliance audit, spill evidence, regulator events, inspection gaps, long downtime, document search, recall, and four write tools (correction, rule, shared note, claim check). Each returns data, citations, flags and drawable visuals. Gemma 4 (26B-A4B, Google AI Studio free tier) uses function calling to choose the tool and fill its arguments, then words the answer. A grounding check accepts the wording only if every number and record ID in it appears in the tool results or the question; otherwise the verified facts are shown. If the model is unreachable, built-in question patterns call the same tools.

**Numbers, documents and notes together.** One "effective value" layer overlays corrections on dataset records, so every tool and every user sees the same corrected data and the original is always one click away. Production status is derived from wellhead minus ambient temperature against the manual's threshold for the well type, never from `recorded_status`. Downtime is 7 days per weekly inspection that found the well not producing; repair `downtime_hours` is ignored. Stops are explained from open repairs and notes ("no recorded reason" when there is none), and compliance joins inspections, regulator events, repair reports and SOP deadlines.

**Memory.** *Shared* (SQLite, persistent): corrections keep the dataset value, the value before, the new value, who, why, when and scope, and a later correction supersedes without deleting; rules are scoped to a well type or one well (a T350 rule never touches T200); shared notes and status claims. *Private:* conversations and "the wells we discussed" are keyed to the signed-in user; the model never supplies a user ID, and another user's chat returns HTTP 403. A correction is previewed (original, proposal, scope, author, reason, effect, conflicting notes) and saved only on confirmation.

**Conflicts and new data.** Disagreements are surfaced, not resolved: a correction that contradicts the inspector's note, two users' claims, or a claim against the latest inspection are flagged (*Conflict*, *Needs confirmation*, *Unconfirmed*) and both statements are kept. Nothing names a well, area, user or answer in code: datasets are listed in `AHC_DATA_DIRS`, tests include a synthetic dataset with IDs that are not in the sample, and an unknown well type reports "rule not found" instead of guessing.

**Verification and audit.** Every answer is checked before it is returned and the verdict is stored: the model's wording must be grounded, citations and record IDs must exist, headline numbers (spill counts and volume, downtime days, production status against the manual's threshold, repair counts and cost, technician by joining users, gas-report deadlines against the SOP) are recomputed from the raw tables, and the question's wording must point to the tool used. Result: PASS (recomputed and agrees), FAIL (a check contradicts the answer) or NEEDS_REVIEW (correctness cannot be established independently). Answers are never rewritten; the generated answer and evidence are kept in a separate SQLite audit table, with a report endpoint and a Verify page. PASS is deliberately rare: it never means the whole answer is right, only that what was checked is.

**Models and cost.** Gemma 4 26B-A4B-IT with minimal thinking, about 2-3K input tokens per question (free tier: 16K per minute, handled by a rolling token budget that skips the optional wording step rather than stalling). No paid services.

**Next.** Evaluate on held-out phrasing, add the production-threshold override as a scoped rule, and a basemap-backed map.

## Page 2: results on the final questions

**Run.** Test dataset from the challenge repository (commit 009e2b5, `test-data/dataset`, today = 15 Jan 2027), loaded alone into a separate database: 600 wells, 7 areas, 6 teams, 27 users, 125,198 inspections, 17,415 repairs, 328 regulator events, 1,887 notes (1,687 operator notes), 4,437 repair reports (every `report_file` present), 3 manuals (T500's 25 °C limit read from its manual) and 9 SOPs. Loaded in 41 s with 0 issues; every count equals a raw recount of the files. The 11 questions (21 turns) ran in order, in the sessions named, with memory kept between sessions: 21 answers, 0 errors, 1,184 s on the free tier (`results/final-results.md`). One fix before the run: the three structured `data_correction` notes in the new data were not applied; they now are (original kept, a user's saved correction still wins; tested). One tool was added after the first pass, for Q3 (re-run in `results/final-results-q3-rerun.md`). Honest summary: the system handles the document-driven rules it was built for; it does **not** yet have tools for most of the new analyses, and in several of those cases the model chose an unrelated tool and showed its output.

**What I would do next, in order:** (1) a supplier-recall and "Parts installed" tool (Q8, Q9); (2) status with OPS-3 precedence and shut-in/restart notes (Q6, Q9); (3) bypass and MOC approval timeline (Q4); (4) read the regulator letter's criteria and apply them to spills (Q5); (5) an operator-note ranking (Q7); (6) per-user preferences (Q8); (7) stop showing a table when its tool is unrelated to the question. What the verification does and does not cover: a number, record ID or person's name in the model's wording that is not in the tool results is replaced by the verified facts, and that held on all 21 turns. It cannot tell whether the right tool was used (Q2, Q5, Q9) or whether a promise is real (Q8's preference).
